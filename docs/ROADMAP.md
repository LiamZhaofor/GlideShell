# GlideShell 路线图

> 状态（2026-10-26）：**1.0.0 已发布**——P0–P7 全部完成，总览与四指切桌面经过多轮真机反馈修正。1.0 之后的方向见第 8 节（对照 macOS 调度中心的差距评估）。本文是唯一的规划来源；每完成一个阶段，在「阶段总览」里更新状态并补上实测结论。

## 1. 产品目标（按优先级）

1. **真正的连续交互**（最高优先级）：手指移动多少，画面推进多少；中途停住，画面停住；反向滑动，画面倒退。**只有松手后**才按距离和速度决定完成还是取消。
2. **重构多任务切换**：三指上滑渐进展开窗口总览；三指横滑跟手切换窗口；四指横滑连续切换虚拟桌面。
3. **macOS 式物理反馈**：惯性、阻尼、弹簧回弹、速度阈值、可打断动画。重点是输入与画面同步，不是堆动画。
4. **高度可定制，保持原生体验**：可配置三/四指手势、灵敏度、排除程序；三指轻点中键、三指拖移等功能互不冲突。
5. **轻量、低延迟、稳定**：首发 Windows 11 精确式触摸板（PTP），不装内核驱动；开机启动、异常恢复、一键退回 Windows 原生手势。

## 2. 接手评估（2026-10-26）

旧原型 MissionFlow（现位于 `legacy/`，基线 tag `missionflow-final`）验证了两件关键的事：Raw Input 能拿到 PTP 触点流，DWM 缩略图能做实时窗口飞行。但它不是可扩展的产品骨架。

### 2.1 与目标的差距

| 目标 | 旧原型现状 | 差距 |
|---|---|---|
| 1 连续交互 | 三指上滑跟手、可逆 | 自适应平滑带来 25–90ms 滞后；速度按消息处理时刻计算；手指未抬就自动提交（顶格 120ms、滑动中快甩），违背「松手才决定」 |
| 2 多任务 | 只有三指上滑总览 | 横滑切换窗口、四指切桌面均未开始 |
| 3 物理 | 固定时长 easeOutCubic | 松手速度不传递给动画，动画不可真正打断 |
| 4 定制 | 阈值 JSON 热重载 | 无手势映射、排除程序、三指拖移、冲突规则 |
| 5 稳定 | 托盘常驻 | 无开机启动、看门狗、原生手势回退；日志同步写盘刷屏 |

### 2.2 有实证的根因

- **看不到抬指**：触摸板每个触点都带 TipSwitch（0D/42）和 Confidence（0D/47）按钮位，旧解析器只读 value caps，从不读这两位。PTP 用最后一份报文里 TipSwitch=0 表示抬指，之后通常不再发 cc=0 报文。于是旧代码堆了静默 250/600ms 决断、500ms 宽限、顶格自动提交等兜底——这是「卡住 / 误取消 / 冻结」一类问题的共同来源。（S1 已真机确认：46 个触摸段全部以 TipSwitch=0 报文结束）
- **输入与渲染同在 UI 线程**：ApplyVisual 中位数约 12ms（含同步 `Update()` 整窗重绘），WM_INPUT 排队后成批处理（处理间隔中位数≈0ms，而设备空闲时约 4ms 一份）。
- **坐标未按物理尺寸**：X/Y 各自归一化到 0–1，本机触摸板 124×76mm，横竖同一数值不等距；触发阈值 ΔY>0.02 只有约 1.5mm，三指轻点的抖动就可能误弹覆盖层。
- **常驻开销**：空闲时每份报文（包括单指移动指针）都做一次全屏检测；全屏时每份报文同步写一行日志（旧日志 3647 行里有 3507 行是这一条）。
- **结构**：状态机、手势判断、窗口枚举、布局、动画、绘制全在 1387 行的 `OverlayForm` 里，加 7 个状态标志。目标 2/3/4 都要在「手势 → 动作 → 动画」之间加层次，原结构加不进去。

### 2.3 决策：分层重建（不是推倒重写）

**保留**（迁移到新结构，迁移时补测试）：
- HidP 按 preparsed data 逐字段解析的路线
- 窗口收录规则：cloaked 位含义、Win11 最小化窗口要用 `GetWindowPlacement`、工具窗/owner 过滤
- ~~WinEventHook 最小化瞬间缓存 PrintWindow 快照~~：实测不需要也做不到（见 4.3「最小化窗口」）
- GNOME workspace.js 式就近布局
- 系统手势注册表编码实证（`ThreeFingerSlideEnabled=0xFFFF` + 方向值）
- `--dump` 窗口收录诊断的思路

**丢弃**：
- `OverlayForm` 的整体结构
- 自适应低通「弹簧」
- 一切静默超时判定、宽限期、手指未抬就提交的逻辑
- WinForms 分层窗口（`Opacity`）+ GDI 每帧绘制
- 线程池定时器帧源（非 vsync 对齐）
- `--simdrag` 脚本曲线（改为录制真实轨迹回放）

**技术栈**：继续 C# / .NET 10。真正的合成由 DWM / DirectComposition 在 GPU 上完成，只要输入热路径零分配，托管代码的性能足够。常驻进程去掉 WinForms 后，再评估 NativeAOT 以降低内存与启动时间。

## 3. 目标架构

```
[输入线程]  消息窗口 + Raw Input（RIDEV_INPUTSINK）
            → 零分配 PTP 解析 → 触点帧 { ScanTime, 触点[id, x/y(mm), tip, confidence] }
                 │ 无锁队列
[Core：纯逻辑，可回放测试]
            手势识别：指数稳定、方向锁定、轻点识别 → 手势事件 { Began/Changed/Ended/Cancelled, 指数, 位移mm, 速度mm/s }
            → 手势仲裁：配置映射、排除程序、冲突规则
            → 交互控制器：Overview / AppSwitcher / DesktopSwitcher（只输出「进度 + 速度」）
            → 物理：速度追踪（ScanTime 最小二乘）、落点预测、带初速度可重定向的弹簧、橡皮筋
                 │ 最新状态快照
[渲染线程]  按合成器时钟取样（DCompositionWaitForCompositorClock / DwmFlush）
            → DirectComposition 视觉树 + DWM 实时缩略图
[系统服务]  窗口目录、快照缓存、虚拟桌面（未公开 COM，按系统版本适配）、前台激活
[平台]      原生手势备份 / 接管 / 还原、开机启动、看门狗进程
```

### 3.1 工程结构

```
GlideShell.slnx
src/
  GlideShell.Core/       纯逻辑：手势识别、仲裁、物理、布局、交互模型（net10.0，禁止 P/Invoke）
  GlideShell.Platform/   Windows 实现：Raw Input、DWM、DComp、虚拟桌面 COM、注册表（net10.0-windows）
  GlideShell/            常驻宿主：托盘、线程编排、配置、控制器装配
tests/
  GlideShell.Tests/      单元测试 + 轨迹回放测试 + 架构守卫测试
tools/
  PtpProbe/              只读探针：打印 PTP 报告描述符、录制与分析输入轨迹
legacy/
  M0/ M1/                旧原型，只读参考，不再加功能
```

### 3.2 约定（所有新代码遵守）

- **单位**：触摸板坐标一律换算成毫米；时间一律用硬件 ScanTime（100µs，处理 16 位回绕），不用消息到达时刻。
- **松手才决定**：完成/取消只在收到抬指信号后判定；手指在板上时画面只跟随，不自动提交。
- **不靠静默猜状态**：没有报文 = 状态不变。确需超时兜底的，只能作为异常恢复路径，并单独记日志计数。
- **依赖方向**：`GlideShell → Platform → Core`；Core 不引用 Windows API（由架构守卫测试强制）。
- **热路径零分配**：输入解析、手势识别、每帧渲染不得分配托管对象。
- **日志**：异步、有界、可分级；热路径只计数不写盘。

### 4.1 P0 结果（2026-10-26）

- 旧原型最后一轮调参已入库，基线 tag `missionflow-final`；M0/M1 移到 `legacy/`，各自 slnx 仍可单独构建（`legacy/Directory.Build.props` 截断根目录设置的继承）。
- 新解决方案 `GlideShell.slnx`：Core（net10.0）/ Platform / GlideShell 宿主 / Tests（xunit v3）/ tools/PtpProbe，`TreatWarningsAsErrors` 开启，SDK 由 `global.json` 固定在 10.0.4xx。
- 架构守卫测试 3 项：Core 不得含 P/Invoke、不得引用 Windows 专属程序集、不得带 `SupportedOSPlatform`。已做反向验证：往 Core 临时加一个 DllImport，测试按预期失败。
- 宿主 `GlideShell.exe` 目前只有空入口（app.manifest 已声明 PerMonitorV2），P2/P3 才接入输入与渲染。
- `tools/PtpProbe` 由接手时的一次性脚本整理而来，本机输出与第 7 节一致。

### 4.2 P2 结果（2026-10-26）

- **Core/Input**：`ScanClock`（16 位 ScanTime 展开，空闲多圈与设备清零用主机时间校正）、`FrameAssembler`（并行 / 混合报告模式组帧，复用实例零分配）、毫米坐标。
- **Core/Gestures**：`GestureRecognizer`——位移取相邻帧「共同触点」的平均位移（落指、抬指、加指不跳变）；抬指只认 TipSwitch=0 或触点消失；没有报文 = 状态不变；手掌（Confidence=0）整段忽略；指数稳定窗口、方向锁定、轻点识别；`Cancelled` 只在 10 秒无报文的异常路径。`GestureMap`（默认表 / 三指拖移表 / 冲突校验）、`GestureRouter`（Possible 预热、Began 选定；排除程序与全屏判定只在这两个时刻各查一次）。
- **Core/Motion**：设备时间上的最小二乘速度、阻尼弹簧解析解、iOS 橡皮筋与减速投影、`InteractiveTransition`（跟踪期间只跟随不提交，松手按投影选目标、以松手速度起弹簧，动画中可打断）。
- **Core/Tracing**：轨迹格式（PtpProbe 与测试共用）与回放；`RecordedTraceTests` 会对 `tests/GlideShell.Tests/Traces/` 下的真机轨迹按场景断言（目前为空、跳过）。
- **Platform/Input**：`PtpInputThread`（专用线程 + 消息窗口，LibraryImport、预分配缓冲，热插拔）。`PtpProbe live` 可实时打印识别结果。
- 阈值已按 S1 真机轨迹校准：滑动阈值 2mm、指数稳定 60ms、轻点 ≤200ms / ≤1mm（原先验值 3mm / 40ms / 250ms / 2mm）。

### 4.3 P3 结果（2026-10-26，首个可运行版本）

- 宿主 `GlideShell.exe`：托盘（单击开关总览；「暂停」= 一键退回 Windows 原生手势；开机启动；打开配置 / 日志；退出）、Ctrl+Alt+O、配置热重载（`%APPDATA%\GlideShell\config.json`）、日志（`%LOCALAPPDATA%\GlideShell\logs`）、看门狗进程（主进程崩溃后按接管记录还原系统手势）、`--restore-native` 紧急还原。
- 只接管**已实现动作**对应的系统手势：切换窗口 / 切换桌面实现之前，三指左右、四指手势仍归系统。
- 呈现：每块屏一个非分层置顶覆盖层（`WS_EX_NOACTIVATE`，永不抢焦点；展开后由低级键盘钩子处理 Esc / Enter），桌面壁纸缩略图打底（其不透明度兼作背景变暗），窗口全部是 DWM 实时缩略图，渲染线程按合成器时钟（`DCompositionWaitForCompositorClock`）逐帧更新。缩略图跨会话复用，只重注册 Z 序变化的部分。
- 实测（热键冒烟测试 + 截屏，本机显示器实际为 165Hz）：帧间隔 P50 6.1ms / P95 6.2ms（旧原型 60Hz 下 P50 15ms / P95 36ms）；预热首次约 78ms（JIT 与首次注册，已改为启动时静默预热）、之后 5.6ms；展开 / 收起 / 背景变暗 / 标题正常，收起后焦点留在原窗口。
- **最小化窗口**（2026-10-26 实测）：DWM 一直保留着窗口最小化前的整幅画面（缩略图源尺寸 = 最小化前的可见边框，任务栏预览与 Alt+Tab 用的就是它），所以最小化窗口照样是实时缩略图，不需要快照。之前显示成「图标卡片」，是因为按最小化后 237×40 的窗口矩形裁了源矩形。另外两点：`EVENT_SYSTEM_MINIMIZESTART` 到达时窗口已经是最小化状态，PrintWindow 只能抓到黑图，旧原型「最小化瞬间截图」的路线在本机不成立；从最大化状态最小化的窗口按工作区大小布局（它会还原成最大化）。最小化窗口不在屏幕上，所以不从「原位」飞出，而是停在平铺位随进度放大、淡入；被选中时才飞向还原位置。DWM 没有留下画面时（如启动即最小化）退回占位卡片。
- **真机反馈修正（2026-10-26）**：收起时被选中窗口的强调放大改为半程最大、两端为 0（原来终点最大，撤层时会「大一下再归位」）；选中的窗口提到缩略图最上层，并且在覆盖层还盖着时先切前台（最小化的无动画还原）、等两帧再撤层（原来像「凭空出现」）；显示覆盖层前先摆好第一帧（原来第一帧是黑底、像闪屏）；总览里三指横滑移动选中项。
- 缩略图后端：默认用共享缩略图视觉（dwmapi#147，见第 6 节），失败自动退回经典缩略图。
- 还差：修正后的真机复测；背景里的桌面图标是否隐藏；多显示器实机验证。输入到上屏延迟已由 S4 测出（晚取样约 1 帧）。

### 4.4 P4 结果（2026-10-26，首个可运行版本）

- 三指横滑：手指向左 = 内容向左 = 下一个窗口进入中央，1:1 跟手；松手按投影吸附最近的窗口并切到前台，停在当前窗口不切换；两端橡皮筋。
- 呈现：前台窗口所在屏中部的圆角横带（Win11 系统背景 + 深色模式），缩略图在横带内平移，横带外不遮挡、背后是实时桌面；选中项标题只在选中项变化时重绘。
- 实测（`--simulate switch` + 截屏）：帧间隔 P50 6.1ms / P95 6.2ms，预热 14ms；横滑 46mm 后松手吸附到第 3 个窗口并切到前台。
- 晚取样（S4 建议）已用于总览与切换条：按刷新周期睡到下一帧起点前 3ms 再取样，取样到上屏约 1 帧。

### 4.5 P5 结果（2026-10-26，首个可运行版本）

- 路线按 S3 推荐：覆盖层负责跟手动画，真实切换用无动画的 `SwitchDesktop`。
- **Core/Desktops/DesktopSwitchController**：位置 p（0 = 当前桌面，±1 = 相邻桌面完全滑入）随手指 1:1 移动，没有额外死区；松手按投影决定切换或弹回，目标限制在当前位置两侧的整数之间（反向甩只会弹回，不会越过当前桌面）；首尾桌面之外橡皮筋；一旦决定切换，动画落定前不再接管新手势。
- **Platform/VirtualDesktops**：专用 MTA 线程执行全部 COM 调用；启动自检（构建号 → 布局、系统代理 DLL 方法数、GetCount 与列表一致、当前桌面在列表里），不通过就整条路线禁用、交还原生四指手势；手写 vtable 的通知接收器即时更新当前桌面与增删；explorer 重启后自动重连。
- **Platform/Desktops/DesktopSwitchPresenter**：每屏一个置顶工具窗口覆盖层（不属于任何虚拟桌面，切换全程可见），左 / 中 / 右三个桌面的壁纸与窗口（其他桌面的窗口也是实时缩略图）拼成一条随位置平移；松手决定切换后立刻在覆盖层下切换真实桌面，动画落定、收到切换通知、再等 3 帧后撤层；焦点交给新桌面最上层的窗口，空桌面交给桌面本身。
- 实测（`--simulate desktop-right / desktop-left` + 截屏，165Hz）：桌面 1 → 2 → 1 往返成功，帧间隔 P50 6.1ms / P95 6.1–6.2ms，预热 19–41ms，切换通知按时到达，焦点交接无告警。
- 还差：真机手势与原生四指切桌面的对比（决定是否默认接管，见第 6 节）；从正常方式启动（开机启动 / 资源管理器双击）时的焦点交接验证。

### 4.6 P6 结果（2026-10-26，部分完成）

- **三指拖移**（`Core/Pointer/DragController`）：三指滑动越过阈值时按下左键、指针跟随、抬指松开；增益 = 基础像素/毫米 × (1 + 加速 × 速度系数)，亚像素余数累积，慢速移动不卡格子；轻点不按键，中键仍归系统。注入用 `SendInput` 绝对坐标，不受系统指针速度与加速影响。
- 开启三指拖移后按 macOS 的做法，总览与切桌面改为四指（`GestureMap.WithThreeFingerDrag`）；接管系统三指滑动，但不碰三指轻点。
- **托盘快捷设置**：三指拖移开关；四指切桌面开关（虚拟桌面自检不通过时置灰）；灵敏度子菜单高 / 标准 / 低（同时调整滑动阈值和总览 / 切换 / 切桌面行程，手改过配置时显示「自定义」）；「不使用手势的程序」子菜单（加入最近一个前台程序、逐个恢复、全部恢复）；全屏时暂停手势。改动写回 `config.json` 并立即生效。
- 冲突规则：`GestureMap.Validate` 拒绝同一（指数, 轴）绑两个动作；只接管已实现且当前可用的动作对应的系统手势。
- **设置窗口**（托盘「设置…」）：Win32 标准控件（Common Controls 6，跟随系统主题），Per-Monitor DPI，Tab / Enter / Esc 导航。左栏：四个手势位置（三 / 四指 × 上下 / 左右）的动作下拉框（上下方向不提供只能横向的动作；开启三指拖移时三指两格固定为拖移、总览自动挪到四指上下）、全屏暂停、不使用手势的程序（从正在运行的程序里挑或手输进程名）；右栏：灵敏度预设与四个行程滑块、总览背景变暗、拖移速度与加速、开机启动。窗口只编辑 `Core/Configuration/SettingsModel`（配置 ⇄ 界面状态，有单元测试），保存时写回配置并立即生效，界面以外的字段（弹簧、5 指绑定等）原样保留；与默认映射一致时不写自定义映射。托盘的三指拖移、四指切桌面开关走同一个模型。用离屏渲染 + PrintWindow 截图检查过 150% 缩放下的布局与点击接线。
- 弹簧参数、识别细节等少用的高级参数仍在 `config.json`（[docs/CONFIG.md](CONFIG.md) 逐项说明），设置窗口里有「打开配置文件…」。

### 4.7 P7 结果（2026-10-26，大部分完成）

- **看门狗**：主进程启动一个 `--watchdog <pid>` 子进程；主进程非正常退出时按接管记录还原系统手势。实测：杀掉主进程后看门狗还原了全部 7 项，注册表与 Explorer 生效值对照无差异。
- **注销 / 关机**：处理完 WM_ENDSESSION 后进程随时会被结束（看门狗也一样），所以在这里同步把系统手势写回注册表（Explorer 也在退出，不调用设置缓存），否则没开开机启动时下次登录会失去系统手势；重启管理器要求关闭时走正常退出。已用模拟消息验证两条路径。
- **一键回退**：托盘「暂停」即还原原生手势；`GlideShell.exe --restore-native` 是不依赖托盘的紧急还原；单实例互斥。
- **开机启动**：HKCU Run。登录早期 Explorer 的设置缓存可能还没就绪：接管时 Refresh 失败就隔 3 / 6 / 9 / 12 秒重试（注册表已写好），都失败才弹提示。
- **安装 / 卸载**：`build/install.ps1` 装到 `%LOCALAPPDATA%\Programs\GlideShell`（开始菜单、开机启动，无需管理员）；`build/uninstall.ps1` 退出实例、用 `--restore-native` 读回确认原生手势、删除启动项与文件（`-Purge` 连配置与日志）。重装即升级：`GlideShell.exe --quit` 通过注册的窗口消息让运行实例正常退出（会还原系统手势），脚本再等看门狗子进程放开文件。已实测覆盖安装（运行中的实例被正常退出后替换）与卸载。
- **发布**：`build/publish.ps1` 产出自包含单文件（裁剪 + ReadyToRun）`GlideShell.exe` 14.0MB。代码已通过 NativeAOT / 裁剪分析（`IsAotCompatible`，警告即错误，JSON 全部源生成）。实测：启动约 0.15s 完成首次预热（38ms），常驻工作集 43MB / 私有 14.7MB，总览渲染 P95 6.1ms。

### S2 原生手势的程序化开关

- 状态：**完成，可以全自动，已经手指验证**（详见 `docs/spikes/S2-native-gestures.md`，验证工具在分支 `claude/spike-s2-native-gestures-8782f9`）。
- 结论：三指 / 四指手势的生效值在 Explorer（twinui.dll）的设置缓存里，注册表只是持久化层，Explorer 不监听它。正确做法 = 写注册表 + 调设置缓存服务的 `Refresh(SettingId)`（与「设置」应用同一路径），可用 `GetValue(SettingId)` 读回校验。只写注册表、广播 `WM_SETTINGCHANGE`、SPI 回写都无效——这就是旧原型「写了不一定生效」的原因。
- 已落地：`Core/NativeGestures`（设置编号表、只接管绑定方向的接管规划、不覆盖用户改动的还原规划）+ `Platform/NativeGestures`（设置缓存连接、先落盘接管记录再写注册表、读回校验、不可用时降级）。`PtpProbe native` 可只读对照注册表值与生效值。
- 手指验证（2026-10-26，用户在本机执行 F1–F8，全部符合预期）：只写注册表时三指上滑没有反应，`Refresh` 后立刻出现任务视图；`FourFingerSlideEnabled=0` 后四指滑动完全不触发；还原后恢复原状；三指轻点（中键）始终不受影响。之后注册表与动手前的导出逐行一致。
- 未测：重启 Explorer 作为降级手段（F9，理论上有效）；多用户 / 远程桌面会话。

### S3 虚拟桌面

- 状态：**完成**（`docs/spikes/S3-virtual-desktop.md`，验证工具在分支 `claude/spike-s3-virtual-desktop-7532a3`）。
- 接口：26300 是 24H2 布局，`IVirtualDesktopManagerInternal` {53F5CA0B…} 25 个方法，用系统代理 DLL 的 MIDL 格式串逐槽核对过。同一 IID 在 23H2 / 24H2 布局不同，**必须按方法数与槽位签名自检**，不通过就禁用 P5、交还原生四指手势。
- `SwitchDesktop`（槽 9）**本身无动画**，5–13ms 返回、一帧切完；动画版（槽 22）不要用（并发可能让 explorer 崩溃）。
- 置顶 `WS_EX_TOOLWINDOW` 覆盖层在无动画切换全程可见；**其他桌面（被 cloak）窗口的 DWM 缩略图照样是实时的**，不需要「离开时截图」。
- 焦点是难点：后台进程切换后焦点留在旧桌面里看不见的窗口上，`SetForegroundWindow` 受前台锁限制。P5 前要用正常方式启动的 GlideShell 做激活实验（候选：有消息队列的线程上 AttachThreadInput、MScholtes 的任务栏中转、UIAccess）。P4 的切换窗口实测 AttachThreadInput 可以激活，但测试进程是从前台应用启动的，可能享受了豁免，不能算定论。
- 原生基线：Win11 原生四指切桌面**本身就跟手**（6–10mm 死区，约 69mm 滑满一屏，可停可退，松手才提交，收尾 150–200ms 固定时长）。P5 必须明显更好（无死区、松手速度传递、与三指同一套物理）才值得默认接管。
- 顺带发现：旧原型 `IVirtualDesktopManager` 的 IID 写错（a5cd82ff），已在主线修正为 a5cd92ff。

### S4 渲染延迟

- 状态：**完成**（`docs/spikes/S4-render-latency.md`，验证工具与原始数据在分支 `claude/spike-s4-render-latency-5ac2c3`）。
- 结论：非分层覆盖层 + 渲染线程 + 合成器时钟可行，渲染线程本身不是瓶颈（每帧 < 1ms、零分配，UI 线程卡死不影响画面）；在渲染线程调用 `DwmUpdateThumbnailProperties` 是可靠的（旧原型「缩略图不动」的问题来自分层窗口）。
- 延迟取决于帧内取样时机：tick 时取样固定 2 帧；晚取样（下一帧起点前留余量）约 1 帧——已落地（`FramePacer`）。
- 已知约束：`DwmUpdateThumbnailProperties` 每秒一次阻塞（N=5 时 6–16ms）；经典缩略图多了 DWM 自己掉帧，165Hz 下尤其明显（N=2 呈现率就降到 0.63）。
- 未公开的共享缩略图视觉（dwmapi#147）在 165Hz、N≤15 下仍能跟满刷新、属性随 DComp Commit 原子生效、没有每秒阻塞——但属于未公开 API，**是否采用待用户决定**（第 6 节）。
- 还没测：全屏覆盖层下的 DWM 呈现率（需用户同意后测）。

| 窗口在总览中有阴影、收起无缝 | 自画阴影与系统阴影对照校准，撤层前后画面一致 | 追平 |
| — | 三指横滑跟手切换窗口（macOS 没有对应的手势，只有 ⌘Tab） | 超出 |
| 帧率 / 延迟 | 跟满 165Hz，P95 6.2ms；晚取样，输入到上屏约 1 帧 | 达标 |

### 8.2 仍有差距的部分

按对日常使用的影响排序：

1. **总览里没有「桌面条」（Spaces 栏）**——最大的差距。macOS 调度中心顶部列出所有空间：
   - 可以新增 / 删除空间；
   - 可以把窗口拖到别的空间；
   - 在调度中心里左右滑动能直接切换空间。
   
   GlideShell 的总览只显示当前桌面，桌面管理还得回到 Windows 任务视图。这正好落在目标 2「重构多任务切换」上。
2. **缺少两个配套手势**：
   - 应用 Exposé：下滑只看当前程序的窗口；
   - 显示桌面：拇指 + 三指张开，窗口飞向屏幕边缘。
   
   两者都能复用总览的场景与物理，做成跟手版本。
3. **总览里的鼠标操作偏少**：
   - 能悬停、点击，但不能拖动窗口（拖到别的桌面），也不能关闭窗口（Windows 任务视图都有）；
   - 没有「按程序分组」选项。
4. **入口不全**：
   - 只有 Ctrl+Alt+O 一个热键，没有触发角；
   - Ctrl+Win+←/→ 仍是系统动画，没有走 GlideShell 的跟手切换。
5. **覆盖面没验证**。只在一台机器上验证过（单屏、150%、165Hz、ASUS 触摸板），以下都没测：
   - 多显示器（macOS 每块屏各有空间栏）；
   - 100 / 125 / 175% 缩放下的阴影；
   - 其他触摸板。
   
   另外，切桌面覆盖层的缩略图还没有阴影。
6. **分发**：
   - 没有正式代码签名，下载后会有「无法验证发布者」；
   - 没有自动更新；
   - 依赖两个未公开接口：虚拟桌面 COM、dwmapi#147。两者都有启动自检和退路，但 Windows 大版本更新后需要复测。

### 8.3 后续方向（建议）

| 版本 | 内容 | 理由 |
|---|---|---|
| **1.1 稳定与覆盖** | 多显示器实机验证与修正；用 `PtpProbe thumbnails --shadow` 在其他缩放比例下校验阴影；切桌面覆盖层改用共享缩略图并画阴影；总览背景里的桌面图标处理 | 小而确定，先把 1.0 的体验铺到更多环境 |
| **1.2 桌面条** | 总览顶部显示所有桌面（实时缩略图）；在总览中四指左右滑切换桌面，总览不退出；拖窗口到桌面缩略图上移动窗口；新增 / 删除桌面 | 最大的功能差距，直接服务目标 2；其他桌面窗口的实时缩略图已验证（S3）；移动窗口、增删桌面的方法在已接入的同一个 COM 接口上，按槽位自检接入即可 |
| **1.3 配套手势与入口** | 应用 Exposé（跟手）、显示桌面（跟手）、总览里关闭 / 拖动窗口、按程序分组选项、触发角、接管 Ctrl+Win+←/→ | 补齐调度中心的完整手势与入口 |
| **对外发布时** | 正式代码签名证书（或 MSIX）、自动更新、Windows 大版本更新后的自检回归清单 | 面向他人分发的前提，与功能开发并行 |
