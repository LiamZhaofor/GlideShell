# GlideShell 路线图

> 状态（2026-10-27）：**1.3.1 已发布**（显示桌面、总览里关闭窗口、删除当前桌面、按程序分组、Ctrl+Win+←/→、触发角，见 4.14），「1.3」一行完成；1.3.0 应用窗口视图（见 4.13）；1.2.2 总览里拖窗口到别的桌面（见 4.12）；1.2.1 总览里四指横滑 macOS 式翻页（见 4.10）；1.2.0 总览桌面条（含新建 / 删除桌面，见 4.10、4.11）；1.1.0 稳定与覆盖，1.0.0 完成了 P0–P7。后续方向见第 8 节（对照 macOS 调度中心的差距评估）。本文是唯一的规划来源；每完成一个阶段，在「阶段总览」里更新状态并补上实测结论。

## 1. 产品目标（按优先级）

1. **真正的连续交互**（最高优先级）：手指移动多少，画面推进多少；中途停住，画面停住；反向滑动，画面倒退。**只有松手后**才按距离和速度决定完成还是取消。
2. **重构多任务切换**：三指上滑渐进展开窗口总览；三指横滑跟手切换窗口；四指横滑连续切换虚拟桌面。
3. **macOS 式物理反馈**：惯性、阻尼、弹簧回弹、速度阈值、可打断动画。重点是输入与画面同步，不是堆动画。
4. **高度可定制，保持原生体验**：可配置三/四指手势、灵敏度、排除程序；三指轻点中键、三指拖移等功能互不冲突。
5. **轻量、低延迟、稳定**：首发 Windows 11 精确式触摸板（PTP），不装内核驱动；开机启动、异常恢复、一键退回 Windows 原生手势。

## 2. 接手评估（2026-10-26）

旧原型 MissionFlow（现位于 `legacy/`，基线 tag `missionflow-final`）验证了两件关键的事：Raw Input 能拿到 PTP 触点流，DWM 缩略图能做实时窗口飞行。但它不是可扩展的产品骨架。

### 2.1 与目标的差距

| 目标 | 旧原型现状 | 差距 |
|---|---|---|
| 1 连续交互 | 三指上滑跟手、可逆 | 自适应平滑带来 25–90ms 滞后；速度按消息处理时刻计算；手指未抬就自动提交（顶格 120ms、滑动中快甩），违背「松手才决定」 |
| 2 多任务 | 只有三指上滑总览 | 横滑切换窗口、四指切桌面均未开始 |
| 3 物理 | 固定时长 easeOutCubic | 松手速度不传递给动画，动画不可真正打断 |
| 4 定制 | 阈值 JSON 热重载 | 无手势映射、排除程序、三指拖移、冲突规则 |
| 5 稳定 | 托盘常驻 | 无开机启动、看门狗、原生手势回退；日志同步写盘刷屏 |

### 2.2 有实证的根因

- **看不到抬指**：触摸板每个触点都带 TipSwitch（0D/42）和 Confidence（0D/47）按钮位，旧解析器只读 value caps，从不读这两位。PTP 用最后一份报文里 TipSwitch=0 表示抬指，之后通常不再发 cc=0 报文。于是旧代码堆了静默 250/600ms 决断、500ms 宽限、顶格自动提交等兜底——这是「卡住 / 误取消 / 冻结」一类问题的共同来源。（S1 已真机确认：46 个触摸段全部以 TipSwitch=0 报文结束）
- **输入与渲染同在 UI 线程**：ApplyVisual 中位数约 12ms（含同步 `Update()` 整窗重绘），WM_INPUT 排队后成批处理（处理间隔中位数≈0ms，而设备空闲时约 4ms 一份）。
- **坐标未按物理尺寸**：X/Y 各自归一化到 0–1，本机触摸板 124×76mm，横竖同一数值不等距；触发阈值 ΔY>0.02 只有约 1.5mm，三指轻点的抖动就可能误弹覆盖层。
- **常驻开销**：空闲时每份报文（包括单指移动指针）都做一次全屏检测；全屏时每份报文同步写一行日志（旧日志 3647 行里有 3507 行是这一条）。
- **结构**：状态机、手势判断、窗口枚举、布局、动画、绘制全在 1387 行的 `OverlayForm` 里，加 7 个状态标志。目标 2/3/4 都要在「手势 → 动作 → 动画」之间加层次，原结构加不进去。

### 2.3 决策：分层重建（不是推倒重写）

**保留**（迁移到新结构，迁移时补测试）：
- HidP 按 preparsed data 逐字段解析的路线
- 窗口收录规则：cloaked 位含义、Win11 最小化窗口要用 `GetWindowPlacement`、工具窗/owner 过滤
- ~~WinEventHook 最小化瞬间缓存 PrintWindow 快照~~：实测不需要也做不到（见 4.3「最小化窗口」）
- GNOME workspace.js 式就近布局
- 系统手势注册表编码实证（`ThreeFingerSlideEnabled=0xFFFF` + 方向值）
- `--dump` 窗口收录诊断的思路

**丢弃**：
- `OverlayForm` 的整体结构
- 自适应低通「弹簧」
- 一切静默超时判定、宽限期、手指未抬就提交的逻辑
- WinForms 分层窗口（`Opacity`）+ GDI 每帧绘制
- 线程池定时器帧源（非 vsync 对齐）
- `--simdrag` 脚本曲线（改为录制真实轨迹回放）

**技术栈**：继续 C# / .NET 10。真正的合成由 DWM / DirectComposition 在 GPU 上完成，只要输入热路径零分配，托管代码的性能足够。常驻进程去掉 WinForms 后，再评估 NativeAOT 以降低内存与启动时间。

## 3. 目标架构

```
[输入线程]  消息窗口 + Raw Input（RIDEV_INPUTSINK）
            → 零分配 PTP 解析 → 触点帧 { ScanTime, 触点[id, x/y(mm), tip, confidence] }
                 │ 无锁队列
[Core：纯逻辑，可回放测试]
            手势识别：指数稳定、方向锁定、轻点识别 → 手势事件 { Began/Changed/Ended/Cancelled, 指数, 位移mm, 速度mm/s }
            → 手势仲裁：配置映射、排除程序、冲突规则
            → 交互控制器：Overview / AppSwitcher / DesktopSwitcher（只输出「进度 + 速度」）
            → 物理：速度追踪（ScanTime 最小二乘）、落点预测、带初速度可重定向的弹簧、橡皮筋
                 │ 最新状态快照
[渲染线程]  按合成器时钟取样（DCompositionWaitForCompositorClock / DwmFlush）
            → DirectComposition 视觉树 + DWM 实时缩略图
[系统服务]  窗口目录、快照缓存、虚拟桌面（未公开 COM，按系统版本适配）、前台激活
[平台]      原生手势备份 / 接管 / 还原、开机启动、看门狗进程
```

### 3.1 工程结构

```
GlideShell.slnx
src/
  GlideShell.Core/       纯逻辑：手势识别、仲裁、物理、布局、交互模型（net10.0，禁止 P/Invoke）
  GlideShell.Platform/   Windows 实现：Raw Input、DWM、DComp、虚拟桌面 COM、注册表（net10.0-windows）
  GlideShell/            常驻宿主：托盘、线程编排、配置、控制器装配
tests/
  GlideShell.Tests/      单元测试 + 轨迹回放测试 + 架构守卫测试
tools/
  PtpProbe/              只读探针：打印 PTP 报告描述符、录制与分析输入轨迹
legacy/
  M0/ M1/                旧原型，只读参考，不再加功能
```

### 3.2 约定（所有新代码遵守）

- **单位**：触摸板坐标一律换算成毫米；时间一律用硬件 ScanTime（100µs，处理 16 位回绕），不用消息到达时刻。
- **松手才决定**：完成/取消只在收到抬指信号后判定；手指在板上时画面只跟随，不自动提交。
- **不靠静默猜状态**：没有报文 = 状态不变。确需超时兜底的，只能作为异常恢复路径，并单独记日志计数。
- **依赖方向**：`GlideShell → Platform → Core`；Core 不引用 Windows API（由架构守卫测试强制）。
- **热路径零分配**：输入解析、手势识别、每帧渲染不得分配托管对象。
- **日志**：异步、有界、可分级；热路径只计数不写盘。

### 4.1 P0 结果（2026-10-26）

- 旧原型最后一轮调参已入库，基线 tag `missionflow-final`；M0/M1 移到 `legacy/`，各自 slnx 仍可单独构建（`legacy/Directory.Build.props` 截断根目录设置的继承）。
- 新解决方案 `GlideShell.slnx`：Core（net10.0）/ Platform / GlideShell 宿主 / Tests（xunit v3）/ tools/PtpProbe，`TreatWarningsAsErrors` 开启，SDK 由 `global.json` 固定在 10.0.4xx。
- 架构守卫测试 3 项：Core 不得含 P/Invoke、不得引用 Windows 专属程序集、不得带 `SupportedOSPlatform`。已做反向验证：往 Core 临时加一个 DllImport，测试按预期失败。
- 宿主 `GlideShell.exe` 目前只有空入口（app.manifest 已声明 PerMonitorV2），P2/P3 才接入输入与渲染。
- `tools/PtpProbe` 由接手时的一次性脚本整理而来，本机输出与第 7 节一致。

### 4.2 P2 结果（2026-10-26）

- **Core/Input**：`ScanClock`（16 位 ScanTime 展开，空闲多圈与设备清零用主机时间校正）、`FrameAssembler`（并行 / 混合报告模式组帧，复用实例零分配）、毫米坐标。
- **Core/Gestures**：`GestureRecognizer`——位移取相邻帧「共同触点」的平均位移（落指、抬指、加指不跳变）；抬指只认 TipSwitch=0 或触点消失；没有报文 = 状态不变；手掌（Confidence=0）整段忽略；指数稳定窗口、方向锁定、轻点识别；`Cancelled` 只在 10 秒无报文的异常路径。`GestureMap`（默认表 / 三指拖移表 / 冲突校验）、`GestureRouter`（Possible 预热、Began 选定；排除程序与全屏判定只在这两个时刻各查一次）。
- **Core/Motion**：设备时间上的最小二乘速度、阻尼弹簧解析解、iOS 橡皮筋与减速投影、`InteractiveTransition`（跟踪期间只跟随不提交，松手按投影选目标、以松手速度起弹簧，动画中可打断）。
- **Core/Tracing**：轨迹格式（PtpProbe 与测试共用）与回放；`RecordedTraceTests` 会对 `tests/GlideShell.Tests/Traces/` 下的真机轨迹按场景断言（目前为空、跳过）。
- **Platform/Input**：`PtpInputThread`（专用线程 + 消息窗口，LibraryImport、预分配缓冲，热插拔）。`PtpProbe live` 可实时打印识别结果。
- 阈值已按 S1 真机轨迹校准：滑动阈值 2mm、指数稳定 60ms、轻点 ≤200ms / ≤1mm（原先验值 3mm / 40ms / 250ms / 2mm）。

### 4.3 P3 结果（2026-10-26，首个可运行版本）

- 宿主 `GlideShell.exe`：托盘（单击开关总览；「暂停」= 一键退回 Windows 原生手势；开机启动；打开配置 / 日志；退出）、Ctrl+Alt+O、配置热重载（`%APPDATA%\GlideShell\config.json`）、日志（`%LOCALAPPDATA%\GlideShell\logs`）、看门狗进程（主进程崩溃后按接管记录还原系统手势）、`--restore-native` 紧急还原。
- 只接管**已实现动作**对应的系统手势：切换窗口 / 切换桌面实现之前，三指左右、四指手势仍归系统。
- 呈现：每块屏一个非分层置顶覆盖层（`WS_EX_NOACTIVATE`，永不抢焦点；展开后由低级键盘钩子处理 Esc / Enter），桌面壁纸缩略图打底（其不透明度兼作背景变暗），窗口全部是 DWM 实时缩略图，渲染线程按合成器时钟（`DCompositionWaitForCompositorClock`）逐帧更新。缩略图跨会话复用，只重注册 Z 序变化的部分。
- 实测（热键冒烟测试 + 截屏，本机显示器实际为 165Hz）：帧间隔 P50 6.1ms / P95 6.2ms（旧原型 60Hz 下 P50 15ms / P95 36ms）；预热首次约 78ms（JIT 与首次注册，已改为启动时静默预热）、之后 5.6ms；展开 / 收起 / 背景变暗 / 标题正常，收起后焦点留在原窗口。
- **最小化窗口**（2026-10-26 实测）：DWM 一直保留着窗口最小化前的整幅画面（缩略图源尺寸 = 最小化前的可见边框，任务栏预览与 Alt+Tab 用的就是它），所以最小化窗口照样是实时缩略图，不需要快照。之前显示成「图标卡片」，是因为按最小化后 237×40 的窗口矩形裁了源矩形。另外两点：`EVENT_SYSTEM_MINIMIZESTART` 到达时窗口已经是最小化状态，PrintWindow 只能抓到黑图，旧原型「最小化瞬间截图」的路线在本机不成立；从最大化状态最小化的窗口按工作区大小布局（它会还原成最大化）。最小化窗口不在屏幕上，所以不从「原位」飞出，而是停在平铺位随进度放大、淡入；被选中时才飞向还原位置。DWM 没有留下画面时（如启动即最小化）退回占位卡片。
- **真机反馈修正（2026-10-26）**：收起时被选中窗口的强调放大改为半程最大、两端为 0（原来终点最大，撤层时会「大一下再归位」）；选中的窗口提到缩略图最上层，并且在覆盖层还盖着时先切前台（最小化的无动画还原）、等两帧再撤层（原来像「凭空出现」）；显示覆盖层前先摆好第一帧（原来第一帧是黑底、像闪屏）；总览里三指横滑移动选中项。
- 缩略图后端：默认用共享缩略图视觉（dwmapi#147，见第 6 节），失败自动退回经典缩略图。
- 还差：修正后的真机复测；背景里的桌面图标是否隐藏；多显示器实机验证。输入到上屏延迟已由 S4 测出（晚取样约 1 帧）。

### 4.4 P4 结果（2026-10-26，首个可运行版本）

- 三指横滑：手指向左 = 内容向左 = 下一个窗口进入中央，1:1 跟手；松手按投影吸附最近的窗口并切到前台，停在当前窗口不切换；两端橡皮筋。
- 呈现：前台窗口所在屏中部的圆角横带（Win11 系统背景 + 深色模式），缩略图在横带内平移，横带外不遮挡、背后是实时桌面；选中项标题只在选中项变化时重绘。
- 实测（`--simulate switch` + 截屏）：帧间隔 P50 6.1ms / P95 6.2ms，预热 14ms；横滑 46mm 后松手吸附到第 3 个窗口并切到前台。
- 晚取样（S4 建议）已用于总览与切换条：按刷新周期睡到下一帧起点前 3ms 再取样，取样到上屏约 1 帧。

### 4.5 P5 结果（2026-10-26，首个可运行版本）

- 路线按 S3 推荐：覆盖层负责跟手动画，真实切换用无动画的 `SwitchDesktop`。
- **Core/Desktops/DesktopSwitchController**：位置 p（0 = 当前桌面，±1 = 相邻桌面完全滑入）随手指 1:1 移动，没有额外死区；松手按投影决定切换或弹回，目标限制在当前位置两侧的整数之间（反向甩只会弹回，不会越过当前桌面）；首尾桌面之外橡皮筋；一旦决定切换，动画落定前不再接管新手势。
- **Platform/VirtualDesktops**：专用 MTA 线程执行全部 COM 调用；启动自检（构建号 → 布局、系统代理 DLL 方法数、GetCount 与列表一致、当前桌面在列表里），不通过就整条路线禁用、交还原生四指手势；手写 vtable 的通知接收器即时更新当前桌面与增删；explorer 重启后自动重连。
- **Platform/Desktops/DesktopSwitchPresenter**：每屏一个置顶工具窗口覆盖层（不属于任何虚拟桌面，切换全程可见），左 / 中 / 右三个桌面的壁纸与窗口（其他桌面的窗口也是实时缩略图）拼成一条随位置平移；松手决定切换后立刻在覆盖层下切换真实桌面，动画落定、收到切换通知、再等 3 帧后撤层；焦点交给新桌面最上层的窗口，空桌面交给桌面本身。

### 4.12 拖窗口到别的桌面（1.2.2，2026-10-27 发布，用户真机确认没问题）

「1.2 桌面条」一行剩下的最后一项。交互按 macOS 调度中心：
- 在总览里按住窗口拖过系统拖动阈值，窗口跟着指针走（按下的那一点贴着指针）。
- 指针进入桌面条展开后的范围，桌面条就展开，不用先碰到收起时的那一条；窗口同时缩到它在桌面缩略图里大小的 1.6 倍，指针下的桌面高亮。
- 放到别的桌面上：窗口飞进那个缩略图里它的位置并淡出，真实窗口立刻移过去，当前页其余窗口重新排版、从原位置补位过去。落定后桌面条刷新，目标桌面那一页也加入这个窗口（翻过去就能看到）。
- 放到「+」上：新建桌面，再把窗口移过去，桌面条与各页按新列表重建。
- 放在别处、或放在当前桌面上：飞回原位。拖动中按 Esc，窗口随收起飞回真实位置。
- 被拖走的是前台窗口时，前台标记交给剩下最上层的窗口（活动阴影跟着它）；收起时焦点也交给它。

实现：
- **接口**：IVirtualDesktopManagerInternal 槽 4 `MoveViewToDesktop` + IApplicationViewCollection 槽 6 `GetViewForHwnd`（公开的 MoveWindowToDesktop 只能移本进程的窗口）。视图集合的方法数（14）与代理核对，不符时只是不能拖，切换、增删桌面照常。`PtpProbe desktops --move` 实测：另一个进程的测试窗口移到相邻桌面再移回，公开接口核对两步都对。
- **场景**（`OverviewScene.Without` / `With`）：窗口下标不变（缩略图注册按下标，不用重建），移走的标成已移走、不画、不参与命中与键盘选择；其余窗口重新排版，新场景记着旧平铺位，按重排进度插值过去。
- **控制器**：拖动、缩小、放下 / 飞回各一个弹簧；拖动中三指手势和四指翻页不接管。
- **呈现**：拖动时把窗口的缩略图分组（连同阴影）挂到桌面条上面一支，拖到桌面条上不被缩略图挡住；放下的动画落定后放回原来的层次。点击改为松开时生效（按下后没拖动才算点击）。
- **验证**：
  - 单元测试覆盖场景移走 / 加入、跟手、缩小、放到别的桌面、飞回、Esc、加到别的页（235 个测试）。
  - 真实鼠标实测（`--simulate overview-hold` + mouse_event，按截图里橙色测试窗口的位置按下），每步截图：
    - 拖到「桌面 2」：桌面条展开、窗口缩小盖在缩略图上、目标高亮；松开后窗口进入桌面 2 的缩略图，当前页补位；
    - 放在别处：飞回原来的平铺位；
    - 拖到「+」：新建桌面 5，窗口在它的缩略图里；
    - 拖到桌面 2 后四指翻到那一页（`--simulate overview-hold-page`）：窗口已排在那一页，标题正常；
    - 不拖直接点击：收起，测试窗口成为前台。
  - 实测建出来的桌面用 `PtpProbe desktops --remove <n>` 删掉，翻页后用 `desktops --switch 1` 切回。

### 4.13 应用窗口视图（1.3.0，2026-10-27 发布，用户真手势确认没问题）

1.3 的第一项（用户选定先做）。macOS App Exposé：收起态三指下滑，只平铺当前程序的窗口。
- **手势**：总览绑定在三指上下这条轴上（整轴都已从系统接管），收起态下沿收起方向滑原来什么也不做，现在打开应用窗口视图。它的展开方向是下、收起是上，同样 1:1 跟手、松手按投影决定。热键、托盘照旧打开普通总览。配置 `overview.appWindows` 可以关掉。
- **当前程序**：前台窗口的进程名；前台不是可切换的窗口（例如桌面）时取最上层的窗口。
- **场景**（`OverviewScene.Focus`）：在预热好的总览场景上把其他程序的窗口标成排除，只给这个程序的窗口排版（排在整个工作区，不留桌面条）。窗口下标不变，缩略图注册直接沿用，不用重新预热。排除的窗口留在原位、随进度淡出，收起时淡回来，撤层前后画面一致。
- **呈现**：这个视图里没有桌面条、不分页，也不能拖窗口。
- **验证**：单元测试覆盖向下展开、向上收起、热键仍是普通总览、关掉配置后不接管、排版与淡出（238 个测试）。`--simulate app-hold` 截图：前台是 Chrome 时只平铺 Chrome 的窗口，其他窗口淡出，背景变暗。

### 4.14 1.3 其余各项（1.3.1，2026-10-27 发布，用户真机确认没问题）

用户要求一并做完 1.3。
- **总览里关闭窗口**：悬停窗口左上角出现关闭按钮（深色圆底白「×」）。共享缩略图模式下是桌面条上面那一支里的图片视觉，盖在缩略图上；经典模式用 GDI 画。点它发 SC_CLOSE，每 50ms 检查一次：窗口没了就原地缩小淡出、其余窗口补位（`OverviewController.RemoveWindow`）；弹出了对话框或 1.5 秒后还在，就收起并切到它。实测：测试窗口关掉，其余窗口补位。
- **删除当前桌面**：「×」对所有桌面都显示。删当前桌面：用删除代替切换（系统删当前桌面会自己切到并入的那个桌面），覆盖层同时放大进入那个桌面后撤层。删打开总览时所在的桌面（翻页之后）：删完总览收起。两种都结束本次会话，不在总览里重排各页。实测：在新建的桌面 4 上打开总览点它的「×」，515ms 撤层，回到桌面 3、剩 3 个桌面。
- **按程序分组**（`overview.groupByApp`，默认关）：就近布局按中心分行、行内按中心排序；排版时把同一程序的窗口都挪到它们的共同中心，排出来就挨在一起，组与组之间仍按位置就近。
- **接管 Ctrl+Win+←/→**（`desktops.takeOverHotkeys`，默认开）：键盘钩子改为多个订阅者共用一个系统钩子，并能收到松开事件。吞掉方向键（连同它的松开），补发一个未分配的虚拟键，免得系统弹出开始菜单。切桌面控制器加了键盘入口：预热读到相邻桌面后立刻提交并播弹簧；没有那一侧的桌面就带初速度弹一下；动画中再按，落定后接着切。总览展开时改为在总览里翻页（`StepPage`）。
- **触发角**（`hotCorners`，默认都不开）：UI 线程每 40ms 读一次指针位置（不装全局鼠标钩子）。停在角上超过 `dwellMs`（100ms）触发一次，离开 24px 才重新可触发；两块屏相接的角不算；按着鼠标键不触发。动作：窗口总览、应用窗口、显示桌面。
- **显示桌面**（新动作 `ShowDesktop`，默认绑四指上下；三指拖移模式下四指上下仍是总览）：
  - 总览控制器加 `OverviewMode.Desktop`，场景用 `OverviewScene.PushAside`：每个窗口沿离屏幕中心最近的方向整个推出所在屏的工作区，进度 0 → 1 跟手滑出。最小化的窗口排除。背景不变暗，没有标题、桌面条与鼠标交互。
  - 落定在 1：真正最小化这些窗口（先关掉 DWM 过渡动画，免得任务栏上露出缩小动画），等它们都最小化、焦点交给桌面，再撤层。最后一帧就是壁纸加桌面图标，撤层无跳变。
  - 桌面显示着时四指上滑：从进度 1 开始往回拉（窗口从屏幕外滑回）；松手决定收起时就在覆盖层下面从下往上依次还原，最上层的最后还原、成为前台，撤层前等它们都还原到位。桌面没显示时四指上滑打开窗口总览（macOS 四指上滑 = 调度中心）。
  - 「桌面显示着」= 上次最小化的窗口都还最小化着，而且前台是桌面。
  - 实测（`--simulate show-desktop-cycle`）：四指下滑后 2 个窗口最小化，只剩桌面；四指上滑后 Chrome 还原成最大化。
- **设置窗口**：加了「触发角」（四个角各一个下拉框）与「总览与切桌面」（应用窗口视图、按程序分组、Ctrl+Win+←/→ 三个开关）。
- 单元测试 251 个。Ctrl+Win+←/→ 用户真机确认正常。
- 用户真机反馈后修正：
  - 显示桌面后拉回，窗口先飞到不对的位置、撤层时闪一下归位：最小化窗口的「原位」是它的还原位置，最大化过的窗口还原后其实是最大化的。改为推开时记下每个窗口最小化前的真实位置，拉回时飞回那里。连拍截图确认：窗口按原尺寸从屏幕边滑回，最后一帧正好落在真实位置。
  - 总览展开时点任务栏上的「^」，托盘溢出区被覆盖层盖住（UIAccess 版的置顶覆盖层排在系统弹出层之上）。前台监视器加了不过滤外壳窗口的原始事件：总览停在展开态时，外壳弹出层（任务栏、托盘溢出区、开始菜单、通知中心）成了前台，或指针在覆盖层外（任务栏上）时别的窗口成了前台，就收起总览（点的是总览里的窗口就收起到它）。翻页切桌面引起的前台变化指针在覆盖层上，不受影响。实测：点「^」后总览收起，溢出区完整露出。
  - 拉回时仍有一点偏差、撤层时小跳一下（第二轮反馈），两个原因：
    - 最小化窗口的缩略图是整个窗口，带着四周透明的调整边框（150% 下每边约 10 像素），塞进可见边框大小的矩形就被缩小、错开了。改为最小化前记下可见边框相对窗口的内缩，最小化时按它裁掉（`ThumbnailLayer.IconicInsets`）。
    - 原来松手时才在覆盖层下面还原窗口：缩略图从「最小化时留下的画面」换成实时画面时会短暂消失，Chrome 还要重绘（先是一片底色），撤层前最后几帧就不对。改为拉回会话一开始（覆盖层盖上、窗口都在屏幕外时）就还原，滑进来的已经是实时画面；拉一半又松回去就重新最小化。
    - 连拍逐帧对比：普通窗口撤层前最后一帧与撤层后像素级一致。最大化的 Chrome 撤层约 50ms 后页面内容自己还会挪约 4 像素（标签栏、地址栏不动），是 Chrome 被覆盖层整个盖住后重新显示时的重绘，不是位置问题。
  - 拉回后下面的窗口跑到了上面（第三轮反馈）：窗口是从下往上异步还原的，各在自己的程序里完成，先后不确定，撤层前又按真实层次重排了缩略图。改为都还原后按推开前记下的层次一次排好（DeferWindowPos），再把原来最上层的窗口切回前台。实测两次：两个重叠的测试窗口加 Claude、Chrome，前后层次一致。
  - 偶尔下滑后再上滑，窗口出现一半就消失（第四轮反馈）：显示桌面落定后要花几百毫秒真正最小化窗口，期间又开始上滑的话，覆盖层已经在跟手往回拉，最小化完却照常撤层、复位。改为：提交前已有新手势接管就先不动；最小化途中开始拉回，就地转成拉回会话（在覆盖层下面还原、覆盖层留着继续跟手）。`--simulate show-desktop-quick`（下滑后 250ms 上滑）两次都走了「最小化途中开始拉回」，窗口全部回来、层次一致。
- **设置窗口点任务栏按钮不到前台**（UIAccess 版一直都有）：系统的消息隔离（UIPI）拦掉了任务栏（普通权限的资源管理器）发来的 WM_SYSCOMMAND 等消息。设置窗口用 ChangeWindowMessageFilterEx 放行 WM_SYSCOMMAND、WM_POPUPSYSTEMMENU、WM_ACTIVATE、WM_NCACTIVATE。实测：点任务栏按钮，设置窗口最小化、再点还原到前台。
- 显示桌面后等一会儿再上滑，偶尔下层窗口盖住上层、撤层时跳一下（第五轮反馈）：最小化的窗口在系统里的层次会按最小化的先后被打乱，拉回会话预热时拍下的层次已经不对，缩略图按错的层次叠，撤层前重排才纠正。改为拉回时缩略图按推开前记下的层次叠；还原后排层次改为从下往上逐个提到最上层（一次性的 DeferWindowPos 遇到一个不让动的窗口整批失效），跳过没响应的程序。
- 设置窗口「点了就消失、任务栏点不出来」（第六轮反馈）：诊断日志与 Z 序显示两个原因。
  - 上一版拉回后排层次用「插在某窗口后面」的 DeferWindowPos 链：插在置顶窗口后面的窗口会变成置顶（实测时测试窗口是置顶的），Claude、Chrome、Clash Verge 被意外设成了置顶，普通窗口再也盖不过它们。已改为从下往上逐个提到普通层最上面（不会改变置顶属性），并把这三个窗口改回了不置顶。
  - UIAccess 版的设置窗口被任务栏激活时，「提到最上层」那一步被消息隔离拦掉：窗口成了前台却压在别的窗口下面，再点任务栏按钮就被当成「最小化活动窗口」。改为设置窗口被激活时自己提到最上层。实测：点到别的窗口后再点任务栏按钮，设置窗口回到最上面。

### 4.15 1.4 精致感（1.4.0，2026-10-27 发布，两轮都经用户真机确认没问题）

1.3.1 之后对照 macOS 评估，剩下的差距主要在「皮肤」：文字与装饰是 GDI 画在覆盖层窗口底层的，跟不上逐帧变化，动画期间只能藏起来、停稳后一下子出现，而且被半透明壁纸压暗。1.4 专攻这一块。
- **文字与装饰搬进合成层**：
  - 新增 Direct2D（DC 渲染目标，软件光栅化）+ DirectWrite 的画布（`DecorCanvas`）。文字用 Windows 11 的 Segoe UI Variable，灰度抗锯齿，中文、表情符号由系统字体回退补上。画好的预乘 BGRA 图上传成 DComp 表面。
  - 合成树多了两支：窗口上面一支画窗口装饰（`WindowDecor`），桌面条上面一支画桌面条装饰（`BarDecor`）。
  - 每帧跟着窗口当前的矩形走、按展开进度淡入，所以翻页、补位、拖动、桌面条展开时都不用藏起来。
  - 悬停框与关闭按钮按时间常数淡入（约 45ms）淡出（约 80ms）；拖动的窗口标题淡去。
  - 圆角框用九宫格拼（`NineSlice`）：取整到像素，接缝不留缝，任意大小都清晰。
  - 视觉按窗口缓存、跨会话复用；文字在会话开始后才画，不拖慢第一帧。
  - 没有 D3D11 或共享缩略图时，仍退回原来的 GDI。
- **窗口标题行**：程序图标 + 标题，浅色字带一圈很淡的深色描边与投影，压在亮壁纸上也看得清。没有画面的最小化窗口的「已最小化」灰卡片，改为圆角卡片 + 居中的大号程序图标。
- **程序图标**（`AppIcons`）：外壳的 IShellItemImageFactory（与开始菜单、任务栏同一来源），在专门的 STA 线程上按需要的像素大小取，按（程序，大小）缓存。程序按 AppUserModelID 区分（找不到「所有应用」里的条目就退回 exe 图标），否则按 exe 路径。商店应用的窗口都在 ApplicationFrameHost 进程里，现在按 AppUserModelID 区分，应用窗口视图与按程序分组不再把它们混成一个程序。
- **桌面条**：桌面名随展开程度从顶部一排滑到缩略图下面。当前 / 悬停桌面的高亮从名字底下的圆角块淡变成缩略图外的框。「+」从小圆块长成与缩略图同高的方块。「×」悬停时淡入。
- **应用窗口视图**：同一块屏上既有普通窗口又有最小化窗口时，最小化的缩小排在底部一排（macOS App Exposé），补位后仍按这个规则。
- **总览里直接换成应用窗口视图**：在总览里点某个窗口下面的标题行（图标 + 标题），换成只看这个程序窗口的视图，不收起。这个程序的窗口从现在的平铺位重排过去，其余窗口在平铺位上淡出，桌面条与其余各页撤掉。之后按应用窗口视图收起（三指上滑）。翻到别的桌面那一页时不换。
- **切桌面时系统的桌面名提示**：调查过，压不掉。切桌面前后枚举所有进程的顶层窗口（每 15ms 一次，实测两次），提示出现时没有任何新窗口出现或取消隐藏，是资源管理器在已有的外壳界面里画的，无法从外部安全地隐藏。保留为已知限制。
- 单元测试 253 个。`--simulate overview-hold` 截图：标题、图标、悬停框、关闭按钮、桌面条文字都在合成层里，150% 下清晰；总览渲染 P95 6.2ms（165Hz），与 1.3.1 相同。用户真机确认第一轮没问题。
- **第二轮**：
  - **应用窗口视图回到总览**：在应用窗口视图里点标题行回到窗口总览，不收起。这个程序的窗口重排回总览里的位置，其他程序的窗口在各自的平铺位淡入（`OverviewScene.ReturnFrom`），桌面条与其余各页重新准备（缩略图层有缓存）。三指下滑直接打开的应用窗口视图也能这样回去。指针在标题行上显示手形。
  - **三指切换条与总览统一**：
    - 缩略图换成带窗口阴影的共享缩略图视觉（原来是经典 DWM 缩略图、每帧同步调用 `DwmUpdateThumbnailProperties`）；居中的那个用活动阴影。
    - 选中框（与总览悬停框同色同样式）跟着连续位置在相邻两项之间滑动。
    - 「程序图标 + 标题」在合成层里按离中心的距离交叉淡化、随手指略微横移（`SwitcherDecor`）。
    - 合成层装饰资源由总览与切换条共用（`SharedThumbnailSource.Decor`）。
    - NativeAOT 实测切换条帧间隔 P50 6.1ms / P95 6.1–6.3ms；用户上一轮真机日志里旧切换条是 P50 10.8ms / P95 12.1ms（跟不上 165Hz）。
  - **首帧卡顿**：渲染循环的统计加上了「最长间隔在第几帧」与「回调本身最长多久」。Debug 版第一帧回调约 14ms，是 JIT；NativeAOT 版回调最长不到 1ms，最长间隔 10–12ms（偶发一帧，合成器那边）。用户第一轮真机日志里总览最长间隔多为 6–7ms，原来展开第一帧的 17–36ms 已经没有了（GDI 标题不再在展开时重绘）。60Hz 屏仍未实测。
  - 单元测试 254 个。

### 4.16 圆角卡片与鼠标按键手势（1.5.0，2026-10-27 发布）

用户在 1.4.0 之后提的两个方向。
- **圆角卡片**（`overview.cornerRadius`，默认 12 DIP）：
  - 缩略图视觉用 DComp 的圆角矩形裁剪（`CreateRectangleClip` = IDCompositionDevice2 槽 22，裁剪对象的数值版 setter 在偶数槽 4–26，按本机 SDK 的 dcomp.h 核对：头文件里先声明的重载在 vtable 里排后面）。
  - 缩略图按源尺寸 1:1 建、整体缩放，所以每帧把屏幕上的半径除以缩放写进去（横纵分开）。
  - 屏幕上的半径按展开进度从窗口自己的（有标题栏 / 可调边框、没最大化的窗口 8 DIP，其余 0）过渡到卡片半径，收起时反过来，撤层前后与真实窗口一致；显示桌面不裁。
  - 悬停框、占位卡片与它同心；桌面条的桌面缩略图取 0.6 倍（放大进入时收成直角）；三指切换条同样圆角。
  - 圆角边缘抗锯齿，阴影在圆角处没有露出深色。
- **鼠标按键手势**（`mouse.button`，默认后退键；`mouse.mmPerDip` 0.2）：
  - 低级鼠标钩子在专门的高优先级线程上（UI 线程忙时整个系统的指针不受影响）。
  - 按下配置的键时吞掉，位移交给 `MouseDragRecognizer`。
  - 拖过 7 像素锁定方向，产生与触摸板一样的手势事件（指数记为 0），由第二个 `GestureRouter` 按「竖直 = 总览、水平 = 切桌面」分给同一套控制器（总览开着时水平 = 翻页）。
  - 没拖开就松开：在钩子回调之外用 SendInput 补发一次原来的按下 + 松开（带标记，钩子放行）。
  - 暂停、排除的程序或全屏程序在前台时不拦截。
  - 模拟实测（SendInput 按住后退键上拖 / 下拖 / 单击，指针下放一个记录鼠标键的测试窗）：上拖打开总览、下拖收起；单击后测试窗收到 XButton1 按下与松开。
  - 用户真机反馈后改为 Mac Mouse Fix 的做法（读了它的 `ModifiedDragOutputThreeFingerSwipe.m`）：
    - 灵敏度太高：原来拖约 275 DIP 切一个桌面。Mac Mouse Fix 横向按「一个屏宽 + 63px 间隙 = 一个空间」换算（空间跟着指针走），竖向按屏高换算。改为横向拖过一个屏宽（加桌面间隙）切过一个桌面、竖向拖过半个屏高完全展开总览，`mouse.mmPerDip` 换成倍数 `mouse.sensitivity`（默认 1）。
    - 不要指针定住：改为指针照常移动；位移取原始输入（RIDEV_INPUTSINK，不带加速、到屏幕边上也有，与 Mac Mouse Fix 用的不带加速位移一致），收不到原始输入时退回钩子里的指针坐标差。
    - 指针变成转圈：窗口类原来没设光标，指针停在切桌面覆盖层上时保持进入前的样子。所有窗口类默认箭头，切桌面覆盖层在 WM_SETCURSOR 里明确设箭头。模拟实测拖动中、展开后都是箭头。
  - 用户选定圆角随窗口缩放（macOS 调度中心里缩略图就是缩小的窗口）：`overview.cornerRadius` 改为窗口原尺寸下的半径（默认 12，范围 0–32），裁剪半径直接写在缩略图视觉自己的坐标系里（不再除以缩放），屏幕上随缩放变小；悬停框、占位卡片、切换条选中框按各自窗口的缩放算圆角（切换条取各项缩放的中位数）。
  - 圆角曲率：DComp 的圆角裁剪只能是圆 / 椭圆弧（与 Windows 11 窗口自己的圆角同一种），不是 macOS 的连续曲率圆角（squircle）。要做连续曲率需要路径裁剪（Windows.UI.Composition 的 CompositionPathGeometry），与现在的 DComp 共享缩略图视觉不在同一套 API 里。
- 设置窗口：「外观」里加了「窗口卡片圆角」，左栏加了「鼠标按键手势」（按住的键、灵敏度）。窗口高度 700 → 830 DIP。
- 单元测试 259 个。

### 4.17 毛玻璃与三指切换飞回（1.5.0，2026-10-27 发布）

用户觉得桌面名底块与三指切换条的灰色背景难看，要透明玻璃效果（开销小），不行就用微软自己的设计语言。
- **桌面名底块：真毛玻璃**（`GlassPatch`）。只取底块那一小块壁纸（外扩 3σ，边缘不发暗）做共享缩略图，挂在一个分组视觉下，分组上加 DComp 高斯模糊（IDCompositionDevice3::CreateGaussianBlurEffect = 24，σ = 12 DIP，边界模式 HARD）和圆角裁剪；下面垫一块不透明黑底，壁纸的不透明度跟总览背景变暗同步，所以和覆盖层里变暗的壁纸一致、只是模糊了。上面再叠 Fluent 的半透明白（当前 14%、悬停 7%）与 1 像素白色描边（16%）。只在桌面条上面单独一支，开销只和底块大小有关。截图确认：当前桌面名底下是模糊的壁纸、淡白描边。
- **三指切换：松手后飞回窗口**（用户反馈：选中的窗口直接弹出来，没有动画）。控制器松手时就开始「飞回」（`SwitcherFrame.Launch`，与吸附同时进行）：选中的缩略图从切换条上的位置飞到窗口的真实位置与大小，圆角从卡片圆角过渡回窗口自己的，其余缩略图、面板、选中框、标题淡出；落定时在覆盖层下面把窗口切到前台（最小化的不播系统动画直接还原），等 DWM 合成一帧再撤层。为此合成层模式下切换条窗口铺满工作区（透明、无 GDI 表面），横带只是其中的面板。飞回途中再滑起来从当前位置接管。选的是当前窗口也一样飞回去再撤层。连拍确认：飞回途中缩略图从横带放大到最大化 Chrome 的位置，落定后与真实窗口一致；松手到撤层约 0.48 秒。用户反馈切换之后闪一下切换条：落定那一帧之后控制器已复位（位置回到 0、飞回进度清零），UI 线程切前台、等一帧合成、撤层期间渲染线程还在按复位后的状态画，整条切换条重新出现几帧。改为渲染线程只画可见的帧（与总览同一个教训）。切到最小化的窗口还会闪一下：落定时才还原，程序重绘前的空白 / 旧画面露出来。改为松手（开始飞回）时就不激活、不播系统动画地还原它并压到最下层（`WindowActivator.RestoreBehind`，置顶窗口不压），程序在飞回的约 0.4 秒里在别的窗口后面重绘好，落定时只需提到前台。
- **三指切换条：Fluent 烟灰面板**。系统的亚克力（DWMSBT_TRANSIENTWINDOW）只在窗口激活时才画，切换条从不激活，所以一直是灰色的「退回色」。试了未公开的 SetWindowCompositionAttribute 模糊（ACCENT_ENABLE_BLURBEHIND / ACRYLICBLURBEHIND）：本机 26300 上连一个前台的普通测试窗口都是纯色（用户目视确认），不可用。改为横带窗口本身完全透明（WS_EX_NOREDIRECTIONBITMAP），合成层里最下面一支画半透明深色圆角面板（88%，12 DIP 圆角）+ 10% 白色描边，后面的内容隐约透出。合成层不可用时退回原来的窗口 + 系统背景 + GDI 标题。

### 4.19 双屏真手势验证（2026-10-28，用户真机确认没问题）

环境：笔记本屏 2560×1600 150% 165Hz 在左（x 为负），外接主屏 2560×1440 125% 200Hz 在右。代码排查 + 实测后修了三处：
- **显示桌面**：原来往离窗口中心最近的屏幕边推，笔记本屏靠右的窗口会被推过两屏相接的那条边、停在外接屏上看得见。现在排除推出去会落到别的屏上的方向，改走最近的另一条边（`OverviewScene.PushAside`，有双屏单元测试）。
- **三指切换飞回**：切换条在前台窗口所在的屏上，合成层透明窗口只铺那块屏的工作区，选中别的屏上的窗口时飞到屏幕边就被裁掉、真实窗口凭空出现。现在透明窗口连同有窗口的其他屏一起铺上（两屏的外接矩形）。实测（`--simulate switch-back`）：窗口铺满两屏，两块屏的任务栏都没有被当成全屏而隐藏。
- **总览里跨屏拖窗口**：按下的覆盖层捕获鼠标，但只有本屏注册了被拖窗口的缩略图，拖过相接处就消失；松开时也只认按下那块屏的桌面条。现在开始拖动时把窗口作为「客人」加进每块屏的缩略图层（`SharedThumbnailLayer.AddWindow`，不算成员、不画标题），悬停与放下按指针所在屏的桌面条；跨屏放进缩略图时按窗口在自己那块屏里的相对位置换算。
- 排查过没问题的：触发角（两屏相接处的角本来就不触发）、设置窗口与 Fluent 菜单跨不同缩放（WM_DPICHANGED / 按所在屏 DPI）、鼠标按键手势（按指针下那块屏的宽度换算）、左屏负坐标下的鼠标坐标。
- 混合刷新率：渲染按一个合成器时钟（这里是 200Hz 的 5ms）取样，165Hz 屏上理论上会有轻微不匀；用户真机看没有问题，暂不按屏分别取样。

### 4.20 Alt+Tab 用切换条（2026-10-28，用户真机确认没问题）

用户要求把 Alt+Tab 纳入。做法：替换系统的 Alt+Tab 界面，用三指切换同一个切换条（同一个 `SwitcherController` / `SwitcherPresenter`），行为照系统的来。
- **拦截**：复用低级键盘钩子（`AltTabHotkeys`，与 Ctrl+Win+←/→ 同一个系统钩子）。按住 Alt（没有 Ctrl / Win）时的 Tab 吞掉；会话中（Alt 还按着）←/→ 移动、Esc 取消、Enter 立即切换、其余按键吞掉；Alt 的松开照常交给系统（否则 Alt 的按键状态卡住），收到松开就切换。每 100ms 确认一次 Alt 还按着（钩子超时被跳过时可能收不到松开）。Ctrl+Alt+Tab 不接管。
- **菜单栏与输入法**：前台程序看到 Alt 按下又松开、中间没有别的键会激活菜单栏；Alt+Shift 之间没有别的键松开会切输入法。开始接管、每次吞键、Shift 按下时都补发一次未分配的虚拟键 0xE8（与 Ctrl+Win 防开始菜单同一招）。
- **行为**：第一次 Tab 选中下一个（Alt+Shift+Tab 从最后一个开始），之后每次一格、两端循环，选中项用切换条的弹簧移到中央；切换条延迟 100ms 才淡入——快速按一下直接切到上一个窗口，不闪出切换条（`KeyRevealDelayUs`）。松开 Alt：没淡入就立刻切换撤层，否则选中的缩略图飞回窗口原位再切（与三指切换同一段飞回）。Esc：当前窗口飞回原位撤层。
- **连按**：上一次的飞回还没落定（约 0.45 秒）又按 Alt+Tab：立刻落定（`FinishLaunch` + 同步撤层），再按新的前台窗口准备场景，否则「上一个窗口」会按旧场景算错。
- **交给系统的情况**：功能关闭（`switcher.takeOverAltTab`，默认开，设置「总览与桌面 → 键盘」）、暂停、排除的程序在前台、全屏暂停、总览或切桌面进行中。普通权限版在管理员程序前台时钩子收不到按键，自然是系统的 Alt+Tab。
- 钩子里只做判断，枚举窗口、准备场景投递到 UI 线程（钩子回调必须很快返回）。
- 还没做：切换条上用鼠标点选（横带是鼠标穿透的）、Alt+Tab 里按 Delete 关窗口。

### S1 输入语义（需要真机手指，约 10 分钟）

- 状态：**完成（2026-10-26）**，结论见 `docs/spikes/S1-input-semantics.md`：抬指总有 TipSwitch=0、静止时不停发、250Hz；滑动阈值 2mm、指数稳定 60ms、轻点 ≤200ms / ≤1mm；修正了「落指初期低置信被当成手掌」导致快甩丢失的问题。
- 工具：`tools/PtpProbe`
  - `record`：专用输入线程 + 消息窗口（RIDEV_INPUTSINK），逐份记录每个触点槽的 ContactId、TipSwitch、Confidence、X/Y，以及 ScanTime、ContactCount、物理按键和到达时刻。按 14 个场景引导，每个场景一个 JSON Lines 文件，默认写到 `artifacts/traces/<时间>/`（已被 git 忽略）。
  - `analyze <目录>`：逐文件统计报告率、成批到达、触摸段（指数变化、落指错开、位移、速度、段内空档、结束方式），并归并成「S1 结论草稿」。
  - `selftest`：注入 1 像素鼠标移动验证消息窗口能收到 WM_INPUT（本机已通过）。
  - `calibrate <目录> [--apply] [--fixtures]`：从轨迹量出轻点时长 / 抖动、落指错开时间，推出 `SlopMm`、`FingerSettleMs`、`TapMaxDurationMs`、`TapMaxMoveMm` 的建议值（在实测最大值上留余量），再把每个场景按当前参数和建议参数各回放一遍、按场景期望判定（`Core/Tracing/ScenarioExpectations`，与回放测试共用），建议参数不更差才推荐；`--apply` 写进配置，`--fixtures` 把轨迹复制成回放测试夹具。已用合成轨迹验证（280ms 的轻点：当前参数漏判，建议参数 4/4 通过）。
  - 录完之后的流程：`PtpProbe calibrate artifacts\traces\<时间> --fixtures` → 看回放对比 → 把建议值改成 `GestureSettings` 的默认值并提交夹具。
  - 分析逻辑已用合成轨迹验证：分段、ScanTime 回绕、静止空档、触点 ID 复用下的抬指判定。
- 场景（`PtpProbe scenarios` 可列出）：单指自检、三指上滑后抬起、三指上滑后停住、三指快甩、三指中途反向、三指下滑、三指横滑、三指轻点、三↔四指切换、手指依次落下、四指上滑、四指横滑、两指滚动、手掌误触。
- 要回答的问题：抬指是否总有 TipSwitch=0 的报文？按住不动时设备是否停发？报告率与成批到达？轻点与滑动的区分阈值？落指错开多久？手掌误触时 Confidence 的表现？
- 产出：结论写进 `docs/spikes/S1-input-semantics.md`；挑选后的轨迹进 `tests/` 作为 P2 回放夹具。

### S2 原生手势的程序化开关

- 状态：**完成，可以全自动，已经手指验证**（详见 `docs/spikes/S2-native-gestures.md`，验证工具在分支 `claude/spike-s2-native-gestures-8782f9`）。
- 结论：三指 / 四指手势的生效值在 Explorer（twinui.dll）的设置缓存里，注册表只是持久化层，Explorer 不监听它。正确做法 = 写注册表 + 调设置缓存服务的 `Refresh(SettingId)`（与「设置」应用同一路径），可用 `GetValue(SettingId)` 读回校验。只写注册表、广播 `WM_SETTINGCHANGE`、SPI 回写都无效——这就是旧原型「写了不一定生效」的原因。
- 已落地：`Core/NativeGestures`（设置编号表、只接管绑定方向的接管规划、不覆盖用户改动的还原规划）+ `Platform/NativeGestures`（设置缓存连接、先落盘接管记录再写注册表、读回校验、不可用时降级）。`PtpProbe native` 可只读对照注册表值与生效值。
- 手指验证（2026-10-26，用户在本机执行 F1–F8，全部符合预期）：只写注册表时三指上滑没有反应，`Refresh` 后立刻出现任务视图；`FourFingerSlideEnabled=0` 后四指滑动完全不触发；还原后恢复原状；三指轻点（中键）始终不受影响。之后注册表与动手前的导出逐行一致。
- 未测：重启 Explorer 作为降级手段（F9，理论上有效）；多用户 / 远程桌面会话。

### S3 虚拟桌面

- 状态：**完成**（`docs/spikes/S3-virtual-desktop.md`，验证工具在分支 `claude/spike-s3-virtual-desktop-7532a3`）。
- 接口：26300 是 24H2 布局，`IVirtualDesktopManagerInternal` {53F5CA0B…} 25 个方法，用系统代理 DLL 的 MIDL 格式串逐槽核对过。同一 IID 在 23H2 / 24H2 布局不同，**必须按方法数与槽位签名自检**，不通过就禁用 P5、交还原生四指手势。
- `SwitchDesktop`（槽 9）**本身无动画**，5–13ms 返回、一帧切完；动画版（槽 22）不要用（并发可能让 explorer 崩溃）。
- 置顶 `WS_EX_TOOLWINDOW` 覆盖层在无动画切换全程可见；**其他桌面（被 cloak）窗口的 DWM 缩略图照样是实时的**，不需要「离开时截图」。
- 焦点是难点：后台进程切换后焦点留在旧桌面里看不见的窗口上，`SetForegroundWindow` 受前台锁限制。P5 前要用正常方式启动的 GlideShell 做激活实验（候选：有消息队列的线程上 AttachThreadInput、MScholtes 的任务栏中转、UIAccess）。P4 的切换窗口实测 AttachThreadInput 可以激活，但测试进程是从前台应用启动的，可能享受了豁免，不能算定论。
- 原生基线：Win11 原生四指切桌面**本身就跟手**（6–10mm 死区，约 69mm 滑满一屏，可停可退，松手才提交，收尾 150–200ms 固定时长）。P5 必须明显更好（无死区、松手速度传递、与三指同一套物理）才值得默认接管。
- 顺带发现：旧原型 `IVirtualDesktopManager` 的 IID 写错（a5cd82ff），已在主线修正为 a5cd92ff。

### S4 渲染延迟

- 状态：**完成**（`docs/spikes/S4-render-latency.md`，验证工具与原始数据在分支 `claude/spike-s4-render-latency-5ac2c3`）。
- 结论：非分层覆盖层 + 渲染线程 + 合成器时钟可行，渲染线程本身不是瓶颈（每帧 < 1ms、零分配，UI 线程卡死不影响画面）；在渲染线程调用 `DwmUpdateThumbnailProperties` 是可靠的（旧原型「缩略图不动」的问题来自分层窗口）。
- 延迟取决于帧内取样时机：tick 时取样固定 2 帧；晚取样（下一帧起点前留余量）约 1 帧——已落地（`FramePacer`）。
- 已知约束：`DwmUpdateThumbnailProperties` 每秒一次阻塞（N=5 时 6–16ms）；经典缩略图多了 DWM 自己掉帧，165Hz 下尤其明显（N=2 呈现率就降到 0.63）。
- 未公开的共享缩略图视觉（dwmapi#147）在 165Hz、N≤15 下仍能跟满刷新、属性随 DComp Commit 原子生效、没有每秒阻塞——但属于未公开 API，**是否采用待用户决定**（第 6 节）。
- 还没测：全屏覆盖层下的 DWM 呈现率（需用户同意后测）。

### 8.2 仍有差距的部分

按对日常使用的影响排序：

1. **总览里没有「桌面条」（Spaces 栏）**——最大的差距。macOS 调度中心顶部列出所有空间：
   - 可以新增 / 删除空间；
   - 可以把窗口拖到别的空间；
   - 在调度中心里左右滑动能直接切换空间。
   
   GlideShell 的总览只显示当前桌面，桌面管理还得回到 Windows 任务视图。这正好落在目标 2「重构多任务切换」上。
2. **缺少两个配套手势**：
   - 应用 Exposé：下滑只看当前程序的窗口；
   - 显示桌面：拇指 + 三指张开，窗口飞向屏幕边缘。
   
   两者都能复用总览的场景与物理，做成跟手版本。
3. **总览里的鼠标操作偏少**：
   - 能悬停、点击，但不能拖动窗口（拖到别的桌面），也不能关闭窗口（Windows 任务视图都有）；
   - 没有「按程序分组」选项。
4. **入口不全**：
   - 只有 Ctrl+Alt+O 一个热键，没有触发角；
   - Ctrl+Win+←/→ 仍是系统动画，没有走 GlideShell 的跟手切换。
5. **覆盖面没验证**。只在一台机器上验证过（单屏、150%、165Hz、ASUS 触摸板），以下都没测：
   - 多显示器（macOS 每块屏各有空间栏）；
   - 100 / 125 / 175% 缩放下的阴影；
   - 其他触摸板。
   
   另外，切桌面覆盖层的缩略图还没有阴影。
6. **分发**：
   - 没有正式代码签名，下载后会有「无法验证发布者」；
   - 没有自动更新；
   - 依赖两个未公开接口：虚拟桌面 COM、dwmapi#147。两者都有启动自检和退路，但 Windows 大版本更新后需要复测。
